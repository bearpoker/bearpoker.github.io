大家好，我是扑克熊 🐻。

最近我完成了一个面向初中数学的学习辅助系统——**错题星**。它既包含错题分析、自主组卷和巩固练习，也提供了一个基于 LangGraph 的智能学习助手。用户不仅可以上传考试资料，让系统识别并分析错题，还可以直接询问 Agent：“这次考试主要错在哪里？”“最近有哪些薄弱知识点？”或者“帮我制定一份 5 道题的练习计划。”

这个 Agent 会根据问题自主读取分析报告、汇总近期薄弱点，并检索教材和题库；当用户需要生成题目或创建巩固任务时，它不会直接写入数据，而是先展示操作内容，等待用户确认后再执行。

一开始，我很容易把这个项目概括成“用 LLM + RAG 生成个性化练习”。但重新梳理代码后，我发现这种说法仍然不够准确：错题星的底层由 **错题分析、组卷、巩固练习三条业务链路**组成，Agent 不是第四条固定流水线，而是连接分析报告、教材、题库和练习任务的智能交互层。

这篇文章会先从全局出发，复盘三条业务链路如何独立工作、如何互相连接，以及 Agent 如何在这些能力之上完成动态工具调用。

## 1. 为什么做这个项目

一开始，我只是想做一个能够识别错题的工具：学生上传考试资料后，系统找出哪些题答错了，再进一步判断这些失分题对应哪些知识点。

但真正开始设计后，我发现“识别错题”并不是一个独立问题。要判断一道题是否答错，系统首先要知道三个信息：**试卷题目是什么、学生写了什么、正确答案是什么**。因此，输入被拆成了试卷、学生作答和标准答案三类，其中只有试卷是必需的，答题卡和标准答案图片都可以选择上传。如果用户没有提供标准答案，或者答案图存在漏识别，系统会使用 AI 补齐，并将相关题目标记为待复核。

找到错题以后，下一个问题是：学生究竟在哪些知识点上失分？只依赖模型自身的知识很难稳定地对应到实际教材目录，所以项目先把知识点整理成章、节、知识点三级目录。分析时，后端会按照年级、学期和教材版本从数据库加载知识点目录，再交给模型完成题目预分类和薄弱点分析，让结果落到明确的知识点上，而不只是一段笼统的错误评价。教材正文的 RAG 检索不参与这一步，它主要用于后续 AI 补题和 Agent 查询教材。

知道薄弱知识点以后，还需要给学生提供对应练习。系统会先从已有题库中寻找符合知识点、题型和难度的题目；题库不足时，再参考教材内容和题库样例生成新题。生成完成也不意味着可以直接展示，题干、选项、答案和解析还要经过质量校验，不合格的题目需要重试或拦截。

这样，最初的“识别错题”逐渐扩展成了一条完整闭环：

```text
识别试卷与作答
→ 获取标准答案并标记待复核项
→ 判定错题
→ 定位失分知识点与错误原因
→ 制定分阶段巩固计划
→ 按知识点生成练习
→ 提交答案并查看结果
```

最后，我又在这些能力之上加入了智能学习助手。它可以关联之前生成的分析报告，继续查询错题和近期薄弱点，检索教材与题库，并为学生整理更有针对性的学习建议和练习计划；用户需要实际生成题目或创建巩固任务时，再通过人工确认进入原有业务流程。

所以，错题星并不是从一开始就按照“LLM + RAG + Agent”的技术组合设计出来的。它更像是从一个具体需求出发，在不断解决数据输入、知识定位、内容生成、质量验证和学习反馈问题的过程中，逐步形成了现在的三条业务链路和智能助手。

## 2. 系统整体架构

```text
链路一：错题分析
试卷 + 标准答案 + 学生作答
→ OCR/视觉识别 → 判分 → 错因诊断 → 薄弱知识点 → 分析报告

链路二：组卷
知识点 + 题型 + 难度 + 题数
→ 题库检索 → 不足时 AI 补题 → 质量校验 → 生成试卷

链路三：巩固练习
分析报告中的巩固计划
→ 转换为组卷配置 → 复用组卷引擎 → 在线作答 → 判分与统计
```

三条链路不是完全割裂的。错题分析会产出巩固建议，巩固练习会复用组卷引擎，而组卷和巩固在题库不足时都会复用同一套教材 RAG、AI 出题和质量校验能力。

项目后端使用 **FastAPI、SQLAlchemy、Pydantic 和 SQLite**，前端使用 **Vue 3、TypeScript、Pinia 和 Element Plus**。OCR 与检索部分使用 **PaddleOCR、FAISS 和 OpenCV**，智能助手则使用 **LangGraph** 编排单 Agent。

## 3. 三条核心业务链路

### 3.1 错题分析链路

错题分析不是把所有内容混在一张图片里处理，而是把输入区分为三类资料，其中试卷必须上传，另外两类可以按实际情况提供：

1. **试卷**：提供题干、题型和题号
2. **标准答案（可选）**：提供判分依据；没有上传或存在漏识别时由 AI 补齐
3. **学生作答（可选）**：提供学生的真实答案和解题过程

我把这三类输入分开处理，再通过 Pydantic Schema 统一成分析管线需要的数据契约。这样做的好处是每类数据的职责清晰：试卷负责“题目是什么”，标准答案负责“正确答案是什么”，答题卡负责“学生答了什么”。需要注意的是，AI 补齐的标准答案目前只会标记为 `needs_review`，多证据验证管线还没有接入这条判分链路，因此用户检查仍然是必要环节。

完成 OCR 或视觉识别后，系统依次执行：

```text
结构化考试数据
→ 对比标准答案并判分
→ 只提取错题进入后续分析
→ 判断主次错因和薄弱知识点
→ 生成分阶段巩固建议
→ 生成面向学生或家长的报告
```

错因不是题目的固定属性。同一道题，不同学生可能分别因为概念混淆、计算错误、审题不清或步骤错误而答错，所以这部分需要结合学生的具体答案动态判断。

分析结果也不只是一段自然语言。它还会给出目标知识点、起始难度、题型、题数和练习策略，这些结构化字段可以继续交给巩固链路使用。

### 3.2 自主组卷链路

自主组卷面向的是一个不同场景：用户不一定有考试分析报告，只想针对某个章节或知识点练习。

用户选择年级、学期、教材版本、知识点、题型、难度和题数后，系统会先校验知识点是否属于当前范围，再逐个题型分区执行组卷：

```text
校验组卷配置
→ 按知识点、题型和难度检索题库
→ 随机采样并跨分区去重
→ 题库不足时调用 AI 补题
→ 对生成题进行质量校验
→ 保存试卷与题目顺序
→ 返回试卷预览
```

这里有一个重要原则：**优先使用已有题库，AI 只负责补足缺口**。如果题库已经有足够的合适题目，就没有必要额外调用模型。

AI 补题也不是只把知识点名称塞进 Prompt。系统分别检索教材知识库和题目库：前者提供知识依据，后者提供可信例题，两者通过知识点 ID 对齐，并不是同一个库。教材知识库通过 FAISS 与精确检索补充定义、方法和上下文，题目库则通过 SQL 按知识点、题型和难度筛选少量 few-shot 样例。生成结果先经过结构与 Prompt 自校验，再进入融合规则、独立模型、SymPy 和本地题库的多证据验证；明确被拒绝的题不会写入数据库，无法自动确认的题则保留为 `draft`，等待后续复核。

因为一次组卷可能触发多次模型调用，耗时可能超过普通 HTTP 请求的等待时间，所以系统采用后台任务：接口先返回任务 ID，前端轮询状态，生成完成后再读取真实试卷。

### 3.3 巩固练习链路

巩固练习从错题分析报告出发，但没有重新实现一套出题逻辑。

分析阶段会生成分阶段练习计划，例如先复习基础概念，再进行同类题强化，最后做综合应用。巩固服务把每个阶段转换成组卷引擎能够理解的 `PaperSection`，然后复用组卷能力：

```text
读取分析报告中的练习计划
→ 按阶段构建题型、难度和知识点配置
→ 后台调用组卷引擎
→ 创建巩固任务
→ 前端轮询至可作答状态
→ 用户逐题提交答案
→ 返回正确率和分阶段统计
```

这条链路复用了组卷中的题库检索、AI 补题、教材 RAG 和质量校验，因此相同的出题规则不会散落在两个模块中。

选择题可以直接比较答案；填空题等存在等价表达的情况，则需要更灵活的判定。完成练习后，系统会汇总各阶段的完成情况和正确率，让一次错题分析真正形成“诊断—练习—反馈”的闭环。

## 4. 教材 RAG 的作用

项目把教材整理成 **29 章、98 节、354 个知识点**的三级目录，并使用 FAISS 建立教材索引。

不过，系统中的数据检索需要明确区分：

- **知识点目录**：通过数据库确定知识点，并限制年级、学期和教材版本
- **教材内容**：通过 FAISS 检索，为模型补充教材定义、方法和例题上下文
- **题库内容**：通过 SQL 按知识点、题型和难度筛选可用题目

RAG 的主要价值不是替代题库，而是在 AI 必须补题或 Agent 需要查询教材时，为模型提供受教材范围约束的上下文。

## 5. Agent 与业务链路的边界

我最初容易把整个项目都描述成 LangGraph Agent，实际上并不准确。

OCR、判分、组卷和巩固任务都是边界明确的后端业务流程，没有必要全部交给模型规划。Agent 是系统之上的自然语言入口：它可以读取本次错题、查询近期薄弱点、检索教材和题库，并预览练习计划。

当前 Agent 有 6 个只读工具和 2 个写操作提案工具。只读操作可以由模型自主选择；生成题目草稿或创建巩固任务会先形成 Pending Action，必须由用户确认后，后端固定执行器才会真正写入数据库。

LangGraph 在这里负责加载最近 12 条消息、执行工具循环、维护状态、暂停确认和从 Checkpoint 恢复；后端则负责权限、参数校验、调用预算、超时、重复调用检测和幂等执行。

可以把三者的职责概括成一句话：

> LLM 决定下一步想做什么，LangGraph 负责让流程按状态运行，后端负责保证操作合法、安全且只能执行一次。

## 6. Agent 评测方法与结果

为了避免只靠几次手动演示判断效果，我先建立了 24 条人工 Ground Truth，覆盖单工具查询、多工具成功链路、写操作确认、短期记忆、身份隔离和失败边界。第一版最终严格通过 23/24，唯一失败来自字符串评分契约过严：模型写的是“5 道”，而评测事实要求连续文本“5道题”。这个结果让我意识到，除了检查模型和工具，评测规则本身也需要审查。

后来，为了覆盖“没有分析报告也能生成题目草稿”的新能力，我增加了 2 条任务，并重新对齐 Fixture、可信报告范围和人工 Ground Truth。当前完整评测结果为：

- 固定任务：**26 条**，其中 18 条使用真实模型、8 条验证确定性服务
- 严格通过：**26/26**
- 工具调用：**42 次**
- 工具选择与必填参数准确率：**100%**
- 写操作人工确认覆盖率：**100%**
- 禁止工具误调用率：**0%**

26/26 只表示这套固定任务全部满足当前评分契约，不代表系统在所有真实用户请求上都能达到 100%。任务规模仍然有限，而且其中 8 条属于确定性服务验证，因此这些数字需要和评测范围一起理解。

## 7. 项目目前的不足

错题星已经跑通了主要能力，但当前仍然是一个单 Agent、每个账户维护单个学生档案、使用本地 SQLite 的面试演示版本。系统已经实现注册登录和认证用户之间的数据隔离，但距离生产环境仍有不少差距：

- 分析任务和部分后台任务仍使用进程内状态，服务重启会丢失
- SQLite 适合本地开发，还没有进行高并发验证
- OCR 错误可能继续传递到判分和诊断阶段
- AI 补齐的标准答案尚未接入多证据验证，只能标记待复核
- RAG 和出题质量还需要更大规模的人工评测
- Agent 使用短期消息恢复，还没有实现长期向量记忆
- 练习是否真正改善长期学习效果仍需要真实用户数据验证

这些边界不会因为接入大模型自动消失，反而需要通过数据契约、状态管理、质量校验和测试逐层控制。

## 8. 总结与后续计划

重新梳理这个项目后，我最大的收获不是“会调用一个 LLM API”，而是理解了怎样拆分一个包含多种输入和不确定结果的 AI 应用：确定性的业务流程交给后端，教材信息通过 RAG 补充，动态工具选择交给 Agent，高风险写操作则必须保留人工确认。
