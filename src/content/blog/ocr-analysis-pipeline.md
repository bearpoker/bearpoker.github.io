大家好，我是扑克熊 🐻。

在上一篇错题星项目复盘中，我从全局介绍了错题分析、自主组卷和巩固练习三条业务链路。这一篇继续深入第一条链路：**一组图片究竟怎样变成一份可以继续生成练习的错题报告？**

这件事看起来像是“上传图片，然后调用 OCR”，但 OCR 只能告诉系统图片里可能写了什么。要判断学生是否答错，至少还要回答三个问题：题目是什么、正确答案是什么、学生实际答了什么。如果这三类信息在输入阶段就混在一起，后面的判分和知识点分析就很难知道每个字段来自哪里，也很难在识别失败时单独降级。

因此，我没有设计一个同时猜测所有内容的识别接口，而是先分离三类输入，再按照题号把结果合并成统一的数据结构。本文会沿着一次真实操作，拆解图片上传、OCR、数据合并、人工核对和报告生成的完整过程。

## 1. 用户在页面上经历了什么

用户进入“试卷分析”页面后，可以上传三类资料：

1. **试卷图片**：必传，最多可以上传多张，例如试卷正反面。
2. **学生答题卡**：可选，用于提取学生答案。
3. **标准答案图片**：可选，系统会优先把它作为判分依据。

页面还允许用户补充年级、学期、已知章节和预估题数。这些信息不会代替识别结果，而是给模型提供更明确的范围。其中年级、学期和教材版本也是后续知识点目录查询的可信边界，不让 OCR 模型自行猜测。

目前页面会提醒用户：虽然系统支持一次上传多张试卷图片，但整张试卷的识别和自动求解更容易积累误差，实际演示时更推荐每次只拍一道题。

用户点击“上传并识别”后，前端会轮询处理状态。识别完成后，页面展示题干、选项、学生答案、标准答案、置信度和待复核标记。用户可以修改标准答案，再点击“开始分析”进入报告页面。

完整操作可以概括为：

```text
选择三类图片
→ 上传并识别
→ 查看结构化题目
→ 核对或修改标准答案
→ 开始分析
→ 等待判分和诊断
→ 查看错题报告与巩固计划
```

## 2. 为什么必须把三类输入分开

三类图片看起来都是考试资料，但它们在系统中的职责完全不同：

| 输入 | 回答的问题 | 写入的主要字段 |
| --- | --- | --- |
| 试卷图片 | 题目是什么？ | `number`、`type`、`stem`、`options` |
| 标准答案 | 正确答案是什么？ | `correct_answer` |
| 学生答题卡 | 学生答了什么？ | `student_answer` |

上传接口从一开始就使用三个独立参数接收文件：`exam_images`、`answer_sheet_image` 和 `answer_key_image`。保存时，每张图片也会记录为 `exam`、`answer_sheet` 或 `answer_key`。因此，后端不需要在识别阶段重新猜测图片类型。

这个设计还让可选输入的降级方式更加明确：

- 没有学生答题卡时，`student_answer` 可以为空，或者回退使用试卷上识别出的手写痕迹。
- 没有标准答案图片时，系统可以让 AI 逐题求解，但必须标记为待复核。
- 标准答案图片只识别出部分题号时，保留已经识别出的答案，只对缺失题号进行 AI 补全。

如果所有资料都交给一次模型调用处理，答案页识别失败可能迫使系统重新识别整张试卷，也很难准确告诉用户哪些答案来自真实图片、哪些答案来自 AI。输入分离以后，每条支路可以独立处理、独立失败，也可以记录自己的来源。

## 3. 三类识别结果如何合并成一道完整题目

系统不会同时启动三条互不相关的识别任务，而是先处理试卷，因为标准答案和学生答案都需要依附在具体题号上。

### 3.1 从试卷中提取题目结构

每张试卷图片首先经过图片预处理，转换成适合识别的 JPEG 字节。随后，PaddleOCR 提取文字块、坐标和字符置信度；图片和 OCR 参考文本再一起交给视觉模型，由模型输出结构化题目。

这里 PaddleOCR 和视觉模型的职责不同：

- PaddleOCR 擅长检测局部文字和位置，提供可追踪的文本块与置信度。
- 视觉模型结合图片布局和 OCR 文字，把内容整理成题号、题干、选项和配图描述。
- 如果 PaddleOCR 不可用或没有检测到文字，流程会降级为视觉模型直接看图，而不是让整个任务失败。

多张试卷图片识别完成后，服务会合并各页结果。遇到重复题号时，保留 OCR 置信度更高的一份，同时保存无法匹配题号的文本区域，供后续人工处理。

此时，一道题的结构大致如下：

```json
{
  "number": 1,
  "type": "single_choice",
  "stem": "下列函数中属于二次函数的是……",
  "options": ["A. ……", "B. ……", "C. ……", "D. ……"],
  "correct_answer": null,
  "student_answer": null,
  "ocr_confidence": 0.94,
  "needs_review": false
}
```

试卷识别只负责先回答“第 1 题是什么”。另外两类答案还没有填入。

### 3.2 按题号关联学生答案

如果用户上传了答题卡，系统会使用专门的学生作答识别 Prompt，提取手写圈选、填涂、字母或数字，输出“题号到学生答案”的映射：

```json
{
  "1": "B",
  "2": "x=3"
}
```

服务遍历已经建立好的题目列表，按照题号把结果写入 `student_answer`：

```python
for question in exam.questions:
    if question.number in answer_map:
        question.student_answer = answer_map[question.number]
```

这一步不会修改标准答案。即使答题卡上的内容识别错误，受影响的也是学生答案支路，不会覆盖题干和正确答案。

### 3.3 按题号关联标准答案

标准答案图片走另一套 Prompt，也返回题号到答案的映射。服务仍然以题号为关联键，但这次写入的是 `correct_answer`：

```python
for question in exam.questions:
    if question.number in answer_map:
        question.correct_answer = answer_map[question.number]
```

如果答案图完整识别成功，整卷的答案来源标记为 `answer_key`；如果只有部分题目识别成功，其余题目由 AI 补齐，则标记为 `partial_success`；没有上传答案图或整张答案图识别失败时，则标记为 `ai_fallback`。

AI 补齐时，系统会保留答案图已经识别成功的题目，只接受缺失题号的生成结果。所有 AI 求解的答案都会把 `needs_review` 设为 `true`，提醒用户当前判分依据并非直接来自标准答案图片。

三路数据合并后，一道题才真正具备判分条件：

```json
{
  "number": 1,
  "type": "single_choice",
  "stem": "下列函数中属于二次函数的是……",
  "options": ["A. ……", "B. ……", "C. ……", "D. ……"],
  "correct_answer": "C",
  "student_answer": "B",
  "ocr_confidence": 0.94,
  "needs_review": false
}
```

## 4. Pydantic Schema 如何形成数据契约

分开识别只能解决数据来源问题，系统还需要保证 OCR 服务、前端页面和分析引擎对每个字段有一致理解。模型返回的是不稳定 JSON：字段可能缺失、类型可能变化，甚至可能把学生答案写进题干。如果后面的服务直接读取这份原始 JSON，每个模块都要重复判断“这个键是否存在”“这个值究竟是什么类型”，错误也会一直拖到判分阶段才暴露。

我在这条链路中设置了两层 Pydantic 契约。第一层描述“图片识别出了什么”，第二层描述“分析服务需要什么”。前端核对页位于两层之间，负责把用户确认后的 OCR 结果显式转换成分析请求。

### 4.1 `StandardizedQuestion`：先固定一道题的语义

OCR 层最小的数据单元是 `StandardizedQuestion`。其中 `number`、`type` 和 `stem` 是必填字段，分别表示题号、题型和题干；其他字段则按来源和场景允许为空：

| 字段 | 含义 | 为什么单独保存 |
| --- | --- | --- |
| `options` | 选择题选项 | 避免把选项混入题干，便于后续按题型处理 |
| `correct_answer` | 判分使用的标准答案 | 与学生答案严格分离，可以记录答案图或 AI 补全结果 |
| `student_answer` | 从答题卡识别出的答案 | 明确表示独立答题卡这一路的结果 |
| `student_handwriting` | 从原试卷空白处识别的手写内容 | 在没有独立答题卡结果时作为学生答案的回退来源 |
| `ocr_confidence` | 本题 OCR 置信度 | 低置信度题目可以在页面上提示复核 |
| `needs_review` | 是否需要人工检查 | 把“不确定性”变成可被前端消费的状态，而不是只写日志 |
| `has_figure`、`figure_desc` | 是否含图及图片描述 | 提醒后续模块不能只依据纯文本理解题目 |

这里最重要的不是字段数量，而是字段不能互相代替。例如，`correct_answer` 表示“系统准备拿什么判分”，`student_answer` 表示“学生提交了什么”，二者即使文本完全相同，也属于不同事实。`student_handwriting` 也不能直接覆盖 `student_answer`，因为前者来自试卷手写区域，后者来自独立答题卡，它们的来源可信度和冲突处理方式不同。

经过这一层后，后续代码面对的不再是一组任意键值，而是一道具有固定语义的题目：

```json
{
  "number": 2,
  "type": "fill_blank",
  "stem": "方程 x²-5x+6=0 的解是____。",
  "options": null,
  "correct_answer": "x=2 或 x=3",
  "student_answer": null,
  "student_handwriting": "x=2",
  "ocr_confidence": 0.91,
  "needs_review": false,
  "has_figure": false,
  "figure_desc": null
}
```

这个例子也说明了“字段完整”和“业务信息完整”不是一回事。对象可以通过 Schema 校验，但学生只写出一个解，是否得分仍然要交给后面的判分逻辑决定。

### 4.2 `StandardizedExam`：给整批识别结果补充上下文

单题结构确定以后，`StandardizedExam` 把所有题目放进同一个上传批次，并补充整卷范围：

- `session_id` 关联本次上传及保存的图片记录；
- `subject`、`grade`、`semester` 和 `textbook_version` 确定后续知识点查询边界；
- `questions` 保存标准化后的题目列表；
- `unmatched_regions` 保留无法归属到题号的 OCR 区域，避免静默丢失；
- `overall_confidence` 描述整卷识别置信度；
- `recognize_status` 说明标准答案来自答案图、部分 AI 补全还是完全 AI 求解；
- `image_paths` 保存需要携带 JWT 才能访问的图片 API 路径。

因此，`StandardizedExam` 不只是“多道题的数组”。它同时保存了追踪信息、教材范围和不确定性来源。分析服务以后需要解释一份报告时，可以知道它属于哪次上传、使用哪个学期的知识点目录，以及标准答案是否经过 AI 补全。

### 4.3 Pydantic 在这里具体拦截什么

Pydantic 会在对象构造和 API 请求解析时完成类型转换与字段校验。当前实现中，以下约束已经直接写进 Schema：

- `ocr_confidence` 和 `overall_confidence` 必须在 0 到 1 之间；
- `grade` 只能是 1 到 3；
- `semester` 只能是 1 或 2；
- `textbook_version` 不能为空，并限制最大长度；
- `questions` 必须是 `StandardizedQuestion` 列表，而不是任意结构；
- `options` 如果存在，必须是字符串列表。

例如，模型返回 `ocr_confidence: 1.4`，或者把 `options` 返回成一个普通字符串，这份数据不能悄悄进入分析管线，而会在 Schema 边界暴露问题。这样，错误会停留在离模型输出最近的位置，排查时也更容易判断是 OCR 解析问题，而不是后面的判分问题。

但 Pydantic 并不自动理解全部业务规则。当前 `type` 和 `recognize_status` 仍然是普通字符串，没有使用 `Literal` 限制所有枚举值；`stem` 也没有设置最小长度。这意味着 Schema 可以保证基本类型和部分范围，却不能单独保证“题型一定合法”“题干一定完整”“答案一定正确”。这些内容仍需要 Prompt 约束、服务逻辑、页面复核和测试共同保证。

### 4.4 前端不是透传，而是一个显式适配层

用户在 OCR 结果页看到的是 `StandardizedExam`。页面先用每道题的 `correct_answer` 初始化可编辑区域；如果用户修改标准答案，点击“开始分析”时，前端会先把修改后的值写回当前 OCR 结果，再进入报告页。

报告页不会把整个 `StandardizedExam` 原样提交给分析接口，而是构造新的 `StartAnalysisRequest`。核心字段映射如下：

```text
StandardizedQuestion.number（整数）
→ String(number)
→ QuestionForGrading.number（字符串）

correct_answer
→ standard_answer

student_answer 存在时优先使用
否则回退到 student_handwriting
→ QuestionForGrading.student_answer
```

题号从整数转成字符串，是因为分析层的题号契约允许表达类似 `2.1` 的子题编号。当前 OCR Schema 仍只接受整数题号，因此这一转换主要统一分析接口的类型，并没有让 OCR 自动获得识别子题号的能力。

学生答案使用“答题卡优先、试卷手写回退”的规则：

```ts
student_answer: q.student_answer || q.student_handwriting || null
```

这条映射把来源优先级固定在前端适配层中。分析引擎只接收一个最终的 `student_answer`，不需要再次判断用户是否上传了答题卡，也不需要知道 OCR 内部有几条识别支路。

### 4.5 `StartAnalysisRequest`：切换到分析业务语言

第二层契约由 `StartAnalysisRequest` 和其中的 `QuestionForGrading` 组成。它不再保存 OCR 置信度、未匹配区域或图片路径，因为这些字段不参与判分；相反，它加入了分析阶段真正需要的内容：

- `standard_answer`：统一后的判分依据；
- `student_answer`：统一后的学生作答；
- `difficulty`：当前前端默认填入 3；
- `max_score`：当前前端默认每题 5 分；
- `knowledge_points`：前端先传空列表，后端再从可信目录中进行预分类。

一次实际转换后的请求大致是：

```json
{
  "exam_title": "二次函数练习",
  "subject": "math",
  "grade": 3,
  "semester": 1,
  "textbook_version": "PEP-CATALOG-V1",
  "questions": [
    {
      "number": "2",
      "type": "fill_blank",
      "stem": "方程 x²-5x+6=0 的解是____。",
      "options": null,
      "standard_answer": "x=2 或 x=3",
      "student_answer": "x=2",
      "difficulty": 3,
      "knowledge_points": [],
      "max_score": 5
    }
  ]
}
```

分析接口再次用 Pydantic 验证这份请求。通过后，知识点预分类、判分和报告生成都围绕 `QuestionForGrading` 工作，不再依赖 OCR 模型的原始响应格式。

### 4.6 两层契约解决的是职责边界

完整的数据流可以概括为：

```text
模型原始 JSON
→ StandardizedQuestion / StandardizedExam 校验
→ 前端展示答案来源并允许用户修正
→ 显式字段映射与默认值补充
→ StartAnalysisRequest / QuestionForGrading 再校验
→ 知识点预分类、判分和报告生成
```

如果只使用一份“大而全”的 Schema，OCR 字段和分析字段会逐渐混在一起：图片路径、置信度、满分、知识点和判分结果都可能出现在同一个对象里，模块很难判断哪些字段由自己负责。两层契约虽然多了一次转换，却让责任更清楚：

- OCR 层回答“从图片中识别到了什么，以及结果有多确定”；
- 前端核对层回答“用户最终确认用哪份答案进入分析”；
- 分析层回答“如何用题目、标准答案和学生答案完成判分与诊断”。

这种设计的价值不是让字段看起来更整齐，而是把错误限制在具体边界。OCR 字段异常在 `StandardizedExam` 构造时暴露，用户修正发生在页面适配层，分析请求不合法则由 `StartAnalysisRequest` 拒绝。每个阶段都只承担自己能够解释的责任。

## 5. 从结构化题目到错题报告

分析接口收到 `StartAnalysisRequest` 后，会启动后台任务，前端每隔一段时间查询进度。核心分析管线按照固定顺序执行四个阶段：

```text
X：知识点预分类
→ D：答案判分
→ E：错因与薄弱知识点定位
→ F：报告生成
```

### 5.1 知识点预分类

OCR 只能识别文字，并不知道一道题对应教材中的哪个知识点。分析开始前，后端会按照年级、学期和教材版本加载知识点目录，然后让模型为每道题匹配 1 到 3 个目录内的知识点。

这里使用的是数据库中的知识点目录，不是教材正文的 FAISS RAG。教材 RAG 主要服务后续 AI 出题和 Agent 教材查询，不能把两条链路混为一谈。

### 5.2 判分

判分阶段比较 `standard_answer` 和 `student_answer`，输出每道题是否正确、是否未作答、得分和简短评语。空答案会按照未作答处理。

这一步看起来简单，但它完全依赖前面的数据质量。如果标准答案是错误的，后面的判分再严谨也只是在稳定地产生错误结果。因此，答案来源提示和人工核对不是界面上的附加功能，而是分析链路的一部分。

### 5.3 错因与薄弱知识点定位

判分以后，只有错题进入重点诊断。系统结合题干、标准答案、学生答案和预分类知识点，分析主要错因、次要错因以及对应的薄弱知识点。

错因不是题目的固定标签。同一道题，有人可能是概念混淆，有人可能是计算错误，也有人可能只是漏写条件。只有把学生答案带入分析，结果才有机会从“这是一道二次函数题”进一步变成“学生在哪个环节出了问题”。

诊断结果还会生成结构化练习建议，包括目标知识点、题型、题数、起始难度和练习策略，为后续巩固练习提供输入。

### 5.4 报告生成

最后一个阶段把判分汇总和薄弱点分析整理成面向学生或家长的报告，包括总体表现、薄弱环节、学习建议和分阶段巩固计划。

报告不是链路终点。用户可以点击报告中的按钮，把巩固计划转换成组卷配置，继续复用题库检索和 AI 补题能力，形成从发现问题到实际练习的闭环。

## 6. 最容易被忽略的风险：错误会沿链路传播 🕳️

这套系统中最需要警惕的，不是某一次 OCR 调用失败，而是一个看似合理的错误被后续模块继续使用：

```text
题干识别错误
→ AI 求出的标准答案错误
→ 学生被错误判分
→ 薄弱知识点定位错误
→ 巩固练习方向错误
```

当前实现通过以下方式降低风险：

- 保存每题 OCR 置信度，低于阈值时标记 `needs_review`。
- 明确展示标准答案来自答案图、部分 AI 补全还是完全 AI 求解。
- AI 求解的标准答案默认进入待复核状态。
- 允许用户在开始分析前修改标准答案。
- 多页重复题号优先保留置信度更高的结果。
- PaddleOCR 不可用时可以降级为纯视觉识别。

但这里仍然存在边界。当前生成题目的多证据验证管线没有接入 OCR 标准答案补全，AI 求解答案主要依靠 `needs_review` 和用户检查控制风险。另外，页面目前可以修改标准答案，但学生答案主要是展示，还缺少同等完整的手动修正入口。

这意味着系统已经做到了“标出不确定性”，但还没有做到“自动消除所有不确定性”。对于会直接影响学习建议的教育场景，这个区别必须说清楚。

## 7. 如何验证这条管线 ✅

我把验证拆成两个层次。

第一层是 OCR 侧，检查视觉模型的结构化结果能否被 `StandardizedExam` 接收，以及试卷、标准答案和答题卡是否分别写入预期字段。这里重点关注漏题、题号错位、低置信度标记和答案来源状态。

第二层是分析侧，使用固定的 `QuestionForGrading` 数据分别测试知识点预分类、判分、错因定位和报告生成。除了包含错题的普通场景，也覆盖全对试卷：当没有错题时，定位阶段应直接返回空分析，而不是为了生成内容而虚构薄弱知识点。

比“接口返回 200”更重要的检查是字段是否在正确阶段保持一致。例如知识点预分类以后，题干、标准答案和学生答案不应该被意外修改；标准答案图只漏掉一题时，AI 补全也不应该覆盖其他已经识别成功的答案。

目前项目已经建立了 OCR 和分析管线测试，但涉及真实图片、PaddleOCR 和远程视觉模型的效果仍然受图片质量与模型状态影响。后续更有价值的工作，是建立一套固定图片集，为题目识别、答案匹配和最终判分分别记录准确率，而不是只看最终是否成功生成报告。

## 8. 项目目前的不足 🌱

重新梳理这一部分代码后，我认为还有几个明确的改进方向：

1. **补充学生答案修改入口**：让用户在识别结果页同时修正标准答案和学生答案。
2. **建立固定 OCR 评测集**：分别统计题目召回、题号匹配、标准答案和学生答案准确率。
3. **加强 AI 标准答案校验**：将可用的规则、SymPy 或独立模型证据接入答案补全链路。
4. **细化多页题号冲突处理**：除了置信度，还可以结合页码、版面顺序和用户确认。
5. **增强报告持久化**：让分析结果能够稳定支持跨时间查询和学生知识点变化追踪。

这些方向并不意味着当前链路不可用，而是说明从“能生成报告”走向“报告值得长期信任”，仍然需要持续补充数据校验和可追踪性。

## 9. 写在最后 ✨

实现错题分析以后，我最大的体会是：**OCR 的真正难点不只是识别文字，而是管理不同来源的数据和它们的不确定性。**

错题星先用试卷建立题目骨架，再按题号填入学生答案和标准答案；Pydantic Schema 把模型输出收敛成明确契约；人工核对和来源标记则阻止不确定结果悄悄进入后续分析。这个思路同样适用于发票、合同、病历等多来源文档场景：先分清每类输入的职责，再设计统一的数据边界，最后讨论模型能力。

下一篇我会继续介绍错题星的出题链路：当题库数量不足时，系统如何同时使用教材知识和可信例题，让 AI 补题不只是“根据知识点随便生成一道题”。
